# Исправления безопасности — 3 ноября 2026

## Изменения

- `/api/auth/2fa/setup` и `/enable` отклоняют запросы при уже включённой 2FA (409). Для перенастройки сначала требуется `/disable` с паролем и действующим TOTP. Неактивные аккаунты отклоняются; операции защищены ограничением частоты.
- Блокировка строки пользователя сериализует изменения MFA, использование recovery-кодов и счётчика ошибок. Резервный код длиной 9 символов принимается и удаляется после использования. Ошибки второго фактора и пароля в `/verify` учитываются при блокировке после 5 попыток на 15 минут.
- Ответ `/api/auth/login` больше не содержит `password_hash`. Обновлён мобильный клиент; старый клиент допускает отсутствие этого поля.
- Мобильный офлайн-проверочный материал: PBKDF2-HMAC-SHA256, 600 000 итераций, случайная соль 16 байт, результат 32 байта. Вычисление вынесено из UI isolate; запись хранится только в FlutterSecureStorage и привязана к имени пользователя. Старые SHA-256 и серверные bcrypt-хеши удаляются при доступе к данным авторизации. Старый SHA-256 не используется для миграции: требуется один успешный онлайн-вход. Выход удаляет новую запись.
- Backend в Compose опубликован только на loopback; staging-порт также ограничен loopback. Nginx продолжает обращаться к backend через Docker-сеть.
- Неизвестные URL получают одну метку `unmatched` в Prometheus вместо отдельных временных рядов для каждого URL.
- Добавлены счётчик результатов входа через MFA и записи о настройке, включении, отключении и использовании recovery-кода. Пароли, JWT и сами коды в эти записи не входят. Доставка уведомлений пока не настроена.

- 36 backend-тестов: `test_security_regressions.py`, `test_auth.py`, `test_health.py` — пройдены.
- 37 мобильных тестов: `auth_service_test.dart`, `api_service_test.dart` — пройдены.
- Анализ четырёх изменённых Dart-файлов: нет ошибок; пять существующих информационных замечаний в `login_screen.dart` (const и BuildContext после await).
- Исходники на сервере до выкладки и внутри действующего старого контейнера совпадали с локальной базой по SHA-256.
- После выкладки: `/health` сообщает healthy / database connected; HTTPS главная — 200; `/api/auth/me` без токена — 403. Хеши трёх исправленных модулей в контейнере совпали с локальными.
- Docker и `ss` подтверждают `127.0.0.1:8000`, DNAT ограничен `127.0.0.1/32`. Внешний запрос не получает HTTP-ответа приложения. TCP-handshake из рабочей среды сам по себе не использован как доказательство закрытого порта.

## Серверная выкладка и откат

Исправления backend развёрнуты на neftcontrol.ru образом `systemapro-backend:security-20261103`, производным от работавшего образа, без переустановки зависимостей. Изменены три Python-модуля, привязка порта и ссылка на образ в серверном `docker-compose.audit.yml`. Frontend не пересобирался; nginx перечитал конфигурацию после перезапуска backend.

Сохранены:

- предыдущий образ `systemapro-backend:before-security-20261103`;
- файлы `/opt/es-td-ngo/security-backup-20261103-105717`;
- скрипт узкой выкладки `tools/deploy-security-20261103.sh` с проверкой базовых хешей и автоматическим откатом при ошибке.

Ручной откат на сервере (вернёт также прежние уязвимые настройки; использовать только при необходимости):

```sh
cd /opt/es-td-ngo
cp security-backup-20261103-105717/backend/*.py backend/
cp security-backup-20261103-105717/docker-compose.yml .
cp security-backup-20261103-105717/docker-compose.audit.yml .
docker compose -f docker-compose.yml -f docker-compose.audit.yml up -d --no-deps --no-build --force-recreate backend
docker exec es_td_ngo_frontend nginx -s reload
curl -fsS http://127.0.0.1:8000/health
```
