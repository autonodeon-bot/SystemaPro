# ADR 0003. Domain engine: выделенный модуль для расчётов по НТД

- **Status:** Accepted
- **Date:** 2026-04-19

## Контекст

Расчёты остаточного ресурса, подготовка заключений ЭПБ, проверка применимых
методов НК — всё это хаотично разложено по UI и генераторам отчётов.
Тестов на бизнес-логику нет. При попытке подтвердить число в отчёте
эксперт вручную перепроверяет.

## Решение

`backend/diagnostic_engine/` — отдельный пакет, где:
- pydantic-модели — контракт вход/выход;
- каждая НТД — отдельный модуль (`rd_09_539.py`, `sa_03_008.py`, `norms_map.py`);
- функции — чистые (без БД, без I/O);
- на каждый путь есть тесты `tests/test_diagnostic_engine.py`.

API-обвязка — в `diagnostic_engine/api.py`, endpoints `/api/diagnostic/*`.

## Почему именно так

- Бизнес-логика отделена от транспорта (HTTP), что позволяет тестировать
  формулы без поднятия FastAPI.
- Добавление новой нормы = новый модуль + запись в `NORMS_MAP` + тесты.
- Единая точка: UI (/api/diagnostic/norms/:type) берёт карту методов
  из того же источника, что и backend.

## Последствия

- В отчётных генераторах вызов расчётов упрощается: импортируем функцию,
  получаем `ResidualLifeResult`, сериализуем в шаблон.
- Минимальная реализация (RD 09-539 + SA 03-008) покрывает ~80 %
  повседневной работы. Последующие нормы (РД 153-39.4-078-01, РД 10-112)
  добавляются по тому же паттерну.
